# Sicherheit

OpenChamber gewährt Zugriff auf Ihren Rechner und Ihren Code. Sperren Sie es also ab, bevor jemand außer Ihnen darauf zugreifen kann. Diese Seite behandelt das UI-Passwort, Passkeys und was Sie wissen sollten, bevor Sie OpenChamber in ein Netzwerk exponieren.

## UI-Passwort setzen

Starten Sie OpenChamber mit einem Passwort, und die Browser-UI fragt danach:

```bash
openchamber --ui-password be-creative-here
```

Sie können es auch über die Umgebungsvariable `OPENCHAMBER_UI_PASSWORD` setzen, statt es in die Befehlszeile zu schreiben. Nach der Anmeldung merkt sich OpenChamber das Gerät für eine Weile, damit Sie nicht jedes Mal gefragt werden.

Setzen Sie immer ein Passwort, wenn die Instanz für andere erreichbar ist — besonders über einen [Tunnel](/tunnels/) oder das öffentliche Internet.

## Passkeys

Sobald ein Passwort gesetzt ist, können Sie Passkeys (Face ID, Touch ID, ein Sicherheitsschlüssel) für eine schnellere Anmeldung hinzufügen. Fügen Sie sie unter **Einstellungen → OpenChamber → Passkeys** hinzu.

Passkeys sind an das aktuelle Passwort gebunden. Wenn Sie das Passwort ändern oder entfernen, werden gespeicherte Passkeys gelöscht und Sie fügen sie erneut hinzu.

## Geräte-Tokens

Geräte, die über [Ein Gerät verbinden](/connect-devices/) gekoppelt werden, authentifizieren sich mit eigenen gerätespezifischen Tokens, nicht mit dem UI-Passwort. Pairing-Links sind nur einmal nutzbar und laufen ab, wenn sie nicht verwendet werden; jedes gekoppelte Gerät wird unter **Einstellungen → Remote-Instanzen → Mit diesem Server verbinden** aufgeführt, wo Sie es jederzeit widerrufen können. Verbindungen von außerhalb laufen über das [Private Relay](/private-relay/), das Ende-zu-Ende verschlüsselt ist und Ihren Traffic nicht lesen kann.

## Bevor Sie es freigeben

- Standardmäßig lauscht OpenChamber nur auf Ihrem eigenen Rechner (`127.0.0.1`). Es braucht eine bewusste Änderung, um breiter zu lauschen, und Sie sollten vorher ein Passwort setzen.
- Für Ihre eigenen Geräte bevorzugen Sie [Pairing](/connect-devices/) mit dem [Private Relay](/private-relay/) — dabei wird überhaupt nichts öffentlich freigegeben.
- Wenn Sie eine öffentliche URL brauchen, verwenden Sie lieber einen [Tunnel](/tunnels/) oder ein privates Netzwerk (z. B. VPN), statt einen Port ins Internet zu öffnen.
- Wenn Sie OpenChamber hinter Ihrem eigenen HTTPS-Server betreiben, sehen Sie sich [Reverse Proxy](/reverse-proxy/) an.

## Enterprise-Modus

Wenn Ihr Team Gesprächsinhalte nur an die Modellanbieter senden darf, die Sie in OpenCode konfiguriert haben, schalten Sie den Enterprise-Modus ein, indem Sie eine Umgebungsvariable für den OpenChamber-Server setzen:

```bash
OPENCHAMBER_ENTERPRISE_MODE=1
```

Für die Desktop-App tragen Sie sie in das Profil Ihrer Login-Shell ein (zum Beispiel `~/.zshrc`); OpenChamber liest diese Umgebung beim Start. In den Einstellungen lässt sich der Modus nicht ausschalten. Wenn er aktiv ist:

- Modellanbieter kommen nur aus Ihrer OpenCode-Konfiguration. Einen Anbieter verbinden, sich bei einem anmelden, einen Schlüssel hinzufügen oder einen eigenen Anbieter anlegen ist in OpenChamber ausgeschaltet; bestehende Konten entfernen oder wechseln funktioniert weiter. Das schließt nur den Weg über die App; die eigentliche Sperre ist die unten beschriebene OpenCode-Richtlinie.
- [Klassifizierungsanbieter (Jev)](/classification-providers/) bleiben aus, auch ein eigener Endpunkt, den jemand in den Einstellungen einträgt. Sicherheitsnetz und Auto werden nicht angeboten, und Sitzungen kommen nur von Hand in Arbeit. Um Jev über Ihre eigene Infrastruktur zu nutzen, legen Sie auf dem Server mit `OPENCHAMBER_JEV_URL` einen Endpunkt fest (dazu `OPENCHAMBER_JEV_MODEL` und, falls er einen braucht, `OPENCHAMBER_JEV_API_KEY`). Er wird zur Voreinstellung, lässt sich weiterhin ausschalten, und etwas anderes kann nicht gewählt werden.
- Vorlesen über OpenAI ist aus. Ein eigener Server für Sprachausgabe oder Transkription muss auf demselben Rechner laufen. Lokale Stimmen und lokale Diktiermodelle funktionieren weiter.
- Push-Benachrichtigungen an Telefone und Browser enthalten nur einen allgemeinen Titel wie „Agent response is ready“, ohne Nachrichtentext oder Sitzungsnamen. Desktop-Benachrichtigungen bleiben auf Ihrem Rechner und behalten den vollständigen Text.
- Update-Prüfungen laufen weiter, damit Sicherheitsfixes Sie weiterhin erreichen, aber sie melden nie Nutzungsdaten, nicht einmal die anonyme Installations-ID.
- [Externe Tunnel](/tunnels/) (Cloudflare, ngrok) sind aus. Ein Tunnelanbieter entschlüsselt den Traffic an seinem Edge und sieht jede Anfrage im Klartext.
- Das [Private Relay](/private-relay/) funktioniert nur über Ihr eigenes Relay. Betreiben Sie ein [selbst gehostetes Relay](https://github.com/openchamber/openchamber-relay) und richten Sie den Server mit `OPENCHAMBER_RELAY_URL=wss://relay.example.com/ws` darauf aus. Auch das gemeinsame Relay kann Ihren Traffic nicht lesen, da es Ende-zu-Ende verschlüsselt ist, aber Ihr eigenes hält die Verbindungsmetadaten und den Weg zu diesem Rechner in Ihrem Netzwerk. Das Koppeln von Geräten im lokalen Netzwerk funktioniert weiter.

Aufgaben des kleinen Modells (Sitzungstitel, Zusammenfassungen, Commit-Nachrichten, die Durchsicht der Änderungen) brauchen keinen besonderen Modus. Sie laufen immer auf dem kleinen Modell, das Sie in den Einstellungen gewählt haben, auf einem kleinen Modell des Anbieters, mit dem Sie gerade arbeiten, oder auf dem Standardmodell aus Ihrer OpenCode-Konfiguration. Sie weichen nie auf einen anderen Anbieter aus, der zufällig ebenfalls verbunden ist.

Welche Modellanbieter überhaupt genutzt werden dürfen, entscheidet OpenCode, nicht OpenChamber. Sperren Sie das mit [OpenCode-Richtlinien](https://opencode.ai/v2/docs/policies/): alle Anbieter verbieten, dann die freigegebenen erlauben.

```jsonc
{
  "experimental": {
    "policies": [
      { "action": "provider.use", "resource": "*", "effect": "deny" },
      { "action": "provider.use", "resource": "anthropic", "effect": "allow" }
    ]
  }
}
```

Ein verbotener Anbieter verschwindet, selbst wenn jemand einen Schlüssel dafür hinzufügt. Legen Sie die Richtlinien in die globale `~/.config/opencode/opencode.jsonc`, wo ein Projekt sie nicht aufheben kann, oder liefern Sie sie aus einem OpenCode-Console-Workspace aus, der das letzte Wort hat. Der Enterprise-Modus deckt ab, was OpenChamber selbst darüber hinaus sendet.

Die Websuchen und Seitenabrufe des Agenten laufen ebenfalls über OpenCode, zum Suchdienst und zu den Seiten selbst. Wenn sie Ihr Netzwerk nicht verlassen sollen, verbieten Sie sie mit derselben Art von Richtlinie:

```jsonc
{ "action": "permission", "resource": "websearch:*", "effect": "deny" },
{ "action": "permission", "resource": "webfetch:*", "effect": "deny" }
```

## Verwandt

- [Ein Gerät verbinden](/connect-devices/) — einmaliges Pairing und gerätespezifische Tokens
- [Private Relay](/private-relay/) — Ende-zu-Ende-verschlüsselter Zugriff von überall
- [Tunnel](/tunnels/) — eine öffentliche URL freigeben, wenn Sie eine brauchen
- [Reverse Proxy](/reverse-proxy/) — OpenChamber hinter Ihrem eigenen Server betreiben
